A guide to reliable webhook delivery with retries, backoff, and dead-letter queues

Webhooks fail all the time: receivers deploy, vendors rate-limit, networks time out. Reliable delivery doesn't mean nothing fails. It means every event is stored, retried sensibly, set aside when it can't get through, and easy to replay once the problem is fixed.

Why webhook delivery breaks

A webhook is a promise that one system will tell another when something changes. That promise gets broken in a handful of predictable ways:

  • The receiving endpoint is down, mid-deploy, or returning errors for a few minutes.
  • The request times out because the receiver does slow work before responding.
  • An upstream vendor rate-limits you, or has an outage of its own.
  • Credentials behind the integration expired, so the event never gets fetched in the first place.
  • The vendor doesn't send webhooks at all, and changes have to be detected by polling.

None of these are exotic. If your design assumes the first attempt succeeds, you'll lose events quietly and find out from a customer.

Persist the event before you deliver it

Write every event to durable storage before the first delivery attempt, then deliver from that record. If the process crashes between "event happened" and "event sent", the event is still there to pick up. This outbox pattern is what makes retries, dead-lettering, and replay possible later.

It also means you deliver at least once, not exactly once. Give every event a stable ID and ask consumers to treat it as an idempotency key, so a duplicate delivery is harmless.

Retry only what deserves a retry

Not every failure is temporary. Retrying a request that can never succeed just burns quota and delays the alert someone needs to see.

Usually retry

  • Connection errors and timeouts
  • 429 Too Many Requests
  • 500, 502, 503, and 504

Usually don't

  • 400 Bad Request
  • 401 and 403, which point to a credential problem
  • 404 and 410, where the target is gone

Treat auth failures as their own signal. A 401 is rarely fixed by waiting; it's fixed by refreshing a token or asking the customer to reconnect.

Back off exponentially, and add jitter

Exponential backoff waits longer after each failed attempt: about one second, then two, then four, and so on up to a cap. That gives a struggling receiver room to recover instead of hammering it at a fixed interval.

Backoff alone isn't enough. If a thousand events fail at the same moment, they'll all retry at the same moment too. Jitter randomizes each delay so retries spread out. A common approach is "full jitter": pick a random wait between zero and the current backoff ceiling. Always cap the maximum delay, so a single event doesn't wait for days between attempts.

Give each vendor its own rules

One global retry policy fits nobody. Vendors differ in rate limits, timeouts, and how they signal that you should slow down. Set rules per vendor, or per endpoint:

  • Honor Retry-After headers whenever they're sent, even if your own schedule says otherwise.
  • Match timeouts to how the receiver actually behaves, not to a single default.
  • Track rate-limit budgets per connected account, so one noisy customer doesn't throttle everyone else.
  • Pause delivery to an endpoint that is failing consistently, rather than retrying each event into the same wall.

Know when to give up: the dead-letter queue

Every retry policy needs an end. Decide up front how many attempts or how much elapsed time an event gets, and when it runs out, move it to a dead-letter queue instead of dropping it or retrying forever.

A useful dead-letter queue keeps the full payload, every attempt with its status code and response, and the reason it gave up. It raises an alert when events land there, and it lets someone redeliver one event or a batch once the cause is fixed. A queue nobody looks at is just a slower way to lose data, so watch its depth like any other production metric.

Make replay a normal operation

Sooner or later a receiver will have a bug that accepted events and processed them wrongly. Being able to replay events by ID, by connection, or by time range turns that from a data-recovery project into a routine fix. Replay only works safely when consumers are idempotent, which is one more reason to send stable event IDs from day one.

Build observability in, not on

You can't fix delivery problems you can't see. Track these from the start rather than adding them after the first incident:

  • Delivery success rate per endpoint and per connected account
  • Attempts per event and time from event to successful delivery
  • Dead-letter queue depth and age of the oldest event
  • Searchable logs of every attempt, with request, response, and timing

When a customer asks "did you send it?", the answer should take seconds to find.

A checklist for reliable webhook delivery

  • Events are persisted before the first delivery attempt
  • Every event has a stable ID consumers can use for idempotency
  • Only transient failures are retried
  • Retries use exponential backoff with jitter and a maximum delay
  • Retry rules can differ per vendor, and Retry-After is honored
  • There is a clear limit, after which events go to a dead-letter queue
  • Dead-lettered events trigger an alert and can be redelivered
  • Events can be replayed by ID or time range
  • Delivery metrics and attempt logs exist from day one
