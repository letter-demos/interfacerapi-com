Retries done right: backoff, jitter, and knowing when to give up

Retrying a failed request sounds simple, but naive retries can turn a small upstream hiccup into a full-blown outage. If a thousand clients all retry every second, the vendor's recovering servers get hammered again immediately.

Exponential backoff spaces attempts further apart each time, and jitter adds randomness so clients do not retry in lockstep. A common pattern is to wait roughly one second, then two, then four, with up to half of each delay randomized.

Equally important is knowing which errors deserve a retry. Timeouts, 429s, and 503s usually do. A 400 or 404 almost never will, and retrying them just wastes quota. Respect Retry-After headers whenever a vendor sends them.

Interfacer applies these rules per connector, since every vendor has its own rate-limit quirks. When retries are exhausted, the event lands in a dead-letter queue where you can inspect it and redeliver once the problem is resolved.
